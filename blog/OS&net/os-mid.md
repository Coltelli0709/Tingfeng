### 虚拟化内存
1. bg
程序变成进程的时候，要把代码、数据放到内存里->要知道内存在哪、怎么放
又∵ 硬件归os管

2. 虚拟化
> os为每个进程提供内存，而这同样是一片虚拟的假象。进程自以为自己拥有一大块连续的内存空间——`虚拟内存空间`。

不希望进程接触到真实内存地址，甚至覆盖别的内存数据
-> os要梳理内存 -> 虚拟化

3. 结构
stack、heap、data、code
> 不同于数据结构的heap，此处的堆是用来排序的

4. 映射
代码打印的是虚拟地址，内存条需要物理地址
-> 需要完成映射
`解决`：首先`不可能只靠操作系统完成`，如果每次访问内存都要进入一次操作系统，从user到kernel，再调用os让os翻译，那真是慢得没法用了！
ps：进入os是一个很慢的操作
`于是我们引入好朋友硬件——MMU(内存管理单元)`，负责在程序访问内存单元时把虚拟地址映射成物理地址。
- os干啥？它不是主角吗？
答：os不负责每次映射，而`负责建立和维护地址映射`

5. 如何映射？
一开始：`base + bound （基址 + 界限）`
显然，这要用一块连续内存。简单粗暴，但是局限性强。

而计算 "物理地址 base + bound" 的过程，由硬件完成，被称为`重定位`。

准确来说，是`程序运行时映射`过去的，这个叫`动态重定位`。
相对地，`静态重定位`就是，高级语言的`程序加载到内存`里转化成指令的时候，指令中的地址就已经是物理地址。但是这样不方便也不灵活，一般只在早期程序里有。

e.g.本来进程甲占用1000~1799(称为地皮A)的，所以base是1000，bound是800，要访问200，就直接和base一加就好了。
但是现在os决定把A给到乙，所以甲要腾地方。
那就：
step1: 通过时钟中断/系统调用夺回控制权，暂停进程
step2: 找块地儿，比如2000~2799(B)。
step3: 直接把A整个copy过去
-> ok，搞定了。

但是这样开销还是太大了，不管是搬来搬去还是有进程占着大块内存却不怎么用 -> `引入分段思想`
分成`逻辑上`不同的段

> 所以，打ACM的时候报错段错误，想到数组越界，就是访问了没有权限之类的内存。

说回分段，现在又要维护属于哪个段。比如前两个bit，00是stack，01是heap，10是data，11是code。然后后边紧接着段内偏移。

当然了，段还可以维护是否向下增长、记录保护位等，当然还有更多。
`关于保护位`：代码段一般只读，因为进程读了放cpu里执行就行了，不用写，所以保护位可以记录更多权限。

但是这样还是会有一些碎片，所以此处有一些算法keyword：
`最优匹配、最快匹配、首次匹配`

到此我们发现，不管连续还是分段，`内存空间碎片化`仿佛必然。
(os:这也是熵增的一部分吗？)
总之分配内存变难了，有没有什么办法彻底消除外部碎片呢？
有的！这是os现在用的方法——`分页`。

### 分页
`是非功过：完美解决了外部碎片的问题，但是也会产生少量的内部碎片。`
summary：直接把虚拟内存空间分割成固定长度的分片，或者说内存单元。(我管你这那的)
而这个内存单元，在虚拟内存中叫`page页`，物理内存重叫`frame页帧`。
映射问题又来了。
-> `pagetable页表`

#### 关于页表
我们同样把#$%#&(听不清)切割成两个部分：前面虚拟页，后面页内偏移。
所以pagetable记录虚拟页。此外还维护保护位、有效位、脏位(dirty)、存在位、参考位等。
为什么需要有效位？-> 进程随时可能切换，切换则原来页面的内容无效了。
脏位：页面从磁盘进来，进入内存之后有没有修改。
这些不细讲
提到了`PTE`、`PTBR(pagetable base rigister列表机制计算器)`

- 问题又来了，页表多大？
出乎意料，可以到十几二十位，也就是说可以有pow(2,20)个页
ps: 页表放内存里
