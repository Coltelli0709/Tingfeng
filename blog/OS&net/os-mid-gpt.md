## 1. 进程模型已经有了，先把几条容易混淆的线接对

- **陷入内核与切换进程**是两件事。A 调用 `read()`，CPU 可以先在内核里替 A 检查参数。数据已经就绪时，内核直接返回给 A。若要等数据，A 阻塞，调度器才可能换另一个任务。时钟中断也给内核一个重新调度的机会，内核可以决定让原任务继续。
- `cin >> x` 只有在输入暂不可用且底层读取需要等待时才会阻塞。如果输入缓冲区已经有数据，这次调用可以直接完成。**就绪**表示能跑、在等 CPU。**阻塞**表示缺少某个事件，即使 CPU 空闲也不能继续。
- **堆区**用来放动态分配的对象，例如 `malloc` 或 `new` 得到的内存。地址空间常画成代码、数据、堆、栈。真题问可执行代码放哪里，答代码段（text）。
- 内存部分保留两个更正。基址和界限模型先检查 `0 ≤ 虚拟地址 < 界限`，再算 `物理地址 = 基址 + 虚拟地址`。页表的有效位描述页表项或映射是否有效，切换进程不会自动把该进程的页表项作废。

## 2. 应用想读文件，怎样让内核帮它做？

```text
应用调用 read(fd, buf, count)
→ 库封装把调用号和参数按约定交给受控入口
→ CPU 进入内核态
→ 内核分派到对应处理函数，检查 fd、权限、用户缓冲区和长度
→ 读取数据或等待 I/O
→ 返回用户态，应用根据返回值决定下一步
```

对普通文件且 `count > 0`，`read()` 返回正数表示此次读到的字节数，返回 0 表示读到文件末尾，返回 `-1` 表示出错。`write()` 也可能只写入一部分。复制文件时，读到多少就把这批数据写完，下一次读取才覆盖缓冲区。

**为什么库函数和系统调用要分开记？** `strlen()` 可以在用户态算完。`printf()` 先格式化，结果可能留在 C 库缓冲区，之后由 `fflush()`、缓冲区填满等条件触发写入。`write()` 成功说明内核已接受相应数据，断电持久性要走额外的同步步骤。

课件用广义的中断概念讲 CPU 怎样把控制权交给内核。设备完成 I/O、时钟到期属于外部硬件中断。执行系统调用指令或发生除零、缺页属于当前指令触发的同步事件。看到真题里的“只能通过中断”，先看题目对“中断”的口径。

### 内核服务都放在哪里？

| 结构 | 沿着一次请求找处理者 | 做判断题时看什么 |
| --- | --- | --- |
| 单体内核 | 系统调用进入内核后，多个内核子系统可以直接协作 | 大量服务在内核态，调用路径直接，故障可能波及整个内核 |
| 分层结构 | 上层调用下层公开的接口 | 上层依赖下层的服务约定，可以隐藏下层实现细节 |
| 微内核 | 应用经微内核的 IPC 向用户态服务发送消息 | IPC 是关键机制，文件系统和驱动等服务可移到用户态。各实现保留的内存管理职责可能不同 |

把**机制**与**策略**分开。时钟中断、保存和恢复寄存器提供切换机制。RR、优先级等规则决定选谁，属于调度策略。系统启动可以按“固件 → 引导程序 → 内核初始化 → 首个用户态进程 → 系统服务”记。程序运行前的“源码 → 编译成目标文件 → 链接解析符号和重定位 → 装载映射并执行”是另一条流程。

## 3. Shell 怎样跑一个命令，父子会共享什么？

```text
Shell 解析命令
→ fork 创建子进程：父拿到子 PID，子拿到 0，失败时调用者拿到 -1
→ 子进程 exec：换成目标程序，PID 不变，成功后从新程序开始运行
→ 父进程 waitpid：等待并回收子进程的退出信息
```

成功的 `fork` 之后，父子各自从返回点继续，先后由调度决定。常见 Linux 实现用写时复制：父子起初可共用部分物理页，某方写普通私有变量时才复制相应页，双方最终各自看到自己的修改。`exec` 成功后，旧程序中写在 `exec` 后面的语句不会运行。**僵尸**是子进程已退出、退出信息还没被回收。**孤儿**是原父进程先退出，仍存在的子进程会被重新托管。

### 为什么两个人都写一个文件，有时覆盖，有时排在后面？

```text
进程中的 fd（编号） → 内核的打开文件描述（保存当前偏移等状态） → 文件本身
```

假设目标是初始为空的普通文件。在每次写入一个字节且写入成功的前提下，比较两种打开顺序。

| 打开顺序 | 写入行为 | 文件可能内容 |
| --- | --- | --- |
| 先 `fork()`，父子各 `open()` | 拿到各自的打开文件描述，偏移都从 0 开始 | `a` 或 `b`，后写的覆盖前写的 |
| 先 `open()`，再 `fork()` | 父子继承的 fd 指向同一个打开文件描述，一次写入会推进双方共享的偏移 | `ab` 或 `ba` |

同进程的线程共享文件描述符表。如果主线程写 `b` 后直接从 `main` 返回，进程会结束，工作线程可能来不及写 `a`，因此还可能只留下 `b`。`pthread_join` 成功后，可以确认被等待的线程已经终止。

### 两个进程都能运行了，数据怎么交过去？

- **共享内存**：双方的虚拟地址映射到同一块共享区域。写入后可以直接从共享区域读取，什么时候能读、谁可以改，仍需要锁或信号量来约定。
- **消息传递**：发送方把消息交给通道，接收方取走。阻塞接收在暂时无消息时等待，非阻塞接收立即返回。邮箱把通信对象变成收发双方认可的公共端点。
- **管道**：`pipe()` 给出读端和写端，`fork()` 后父子都可能持有两端。假设父写子读，父关读端，子关写端。只有管道数据读完且所有写端都关闭，读者才看到 EOF。TCP 也提供字节流，应用用长度或分隔符定义消息边界。
- **Socket 与 RPC**：Socket 提供通信端点，TCP 连接建立后可读写字节流。RPC 把调用参数编码、传给服务端执行，再解码结果。超时只表示调用方没按时收到回复，服务端可能已经执行过。

## 4. 一个进程里，为什么还需要线程？

接收请求的线程如果一直等某次 I/O，后来的请求也会堵在它身后。把工作交给另一个线程，接收线程就可以继续接请求。**进程组织资源，线程保存一条执行流的状态。**

| 一般由同进程的线程共享 | 每条线程各有一份 |
| --- | --- |
| 代码、全局数据、堆、虚拟地址空间、打开的文件 | PC、寄存器、栈与栈指针、线程局部存储、调度状态 |

单核可以靠交错执行做到**并发**，多核上不同线程可以在同一时刻**并行**。同一组数据分给多个核做同样的操作叫数据并行。把读取、解码、分析交给不同任务叫任务并行。

### 线程由谁安排？

- **多对一**：线程库把多条用户线程映到一条内核线程。一个阻塞式系统调用若阻塞了唯一的内核线程，其他用户线程也失去执行机会，同一时刻也只能使用一个核。
- **一对一**：每条用户线程对应一条内核线程，可由内核独立调度。Linux 常见的 Pthreads 实现采用这类映射。
- **多对多**：用户态把多条用户线程复用到若干内核线程。两级模型还允许部分用户线程专门绑定一条内核线程。
- **线程池**：提交任务 → 任务进队列 → 空闲工作线程取出 → 执行完成 → 继续取下一项。`pthread_create` 启动执行，`pthread_join` 等待终止。Java 的 `start()` 创建新的执行路径，直接调用 `run()` 在当前线程执行。

### 加核会快多少？

固定工作量中，串行比例为 `s`，并行部分理想地均分给 `n` 个核，加速比为 `1 / (s + (1-s)/n)`。比如 `s=1/4`，4 核的加速比是 `16/7 ≈ 2.29`，核数无限增加时上限为 `1/s = 4`。线程管理和同步的实际成本也会影响速度。

分治任务可以先 fork 子任务，再 join 合并结果。OpenMP 的 `parallel for` 把循环迭代分给不同线程，`reduction` 让各线程先算自己的局部结果，再合并成总结果。共享变量直接累加时，需要考虑竞争条件，见第 6 节。

## 5. 多个任务都想运行，CPU 先交给谁？

调度器决定选谁，分派程序负责执行切换。任务发起阻塞 I/O 或退出，CPU 要重新找工作。时间片到期时，可把当前任务放回就绪队列。等待中的任务完成 I/O 会回到就绪队列，在抢占式策略下还可能立即抢占正在运行的任务。

| 策略 | 在当前就绪任务里怎样选 | 例题常问 |
| --- | --- | --- |
| FCFS | 先到先运行，通常等当前任务完成或阻塞才换 | 长任务先占住 CPU，后面一串短任务一起等，形成护航效应 |
| 非抢占 SJF | CPU 空出来时，选下一段 CPU 执行时间最短的任务 | 只比较已经就绪的任务。任务同时到达、已知长度时，短的排在前面可降低平均等待 |
| SRTF（也叫 STCF） | 新任务到达时，比较剩余执行时间 | 新任务更短时可抢占。在已知执行时间、单核、忽略切换开销的常见模型下，它优化平均周转时间 |
| 非抢占优先级 | CPU 空出来时，从就绪队列选优先级最高的任务 | 数字大还是小代表高优先级，以题面为准。低优先级任务可能饥饿，可随等待时间提高优先级（老化） |
| RR | 取队首最多跑一个时间片，未完成且仍可运行则入队尾 | 关注同一时刻到达和回队的次序。时间片长时接近 FCFS，短时切换较频繁 |
| HRRN | 选响应比 `(等待时间 + 执行时间) / 执行时间` 最大者 | 等得越久，响应比越高。19–20 判断题考它同时考虑等待和执行时间 |

### 用同一组任务走一遍

每个任务只有一段 CPU 执行时间，单核、无切换开销。优先级数字越大越高。RR 的时间片为 2，同一时刻先让新任务入队，再放入刚用完时间片的任务。

| 任务 | 到达时刻 | 执行时间 | 优先级 |
| --- | ---: | ---: | ---: |
| A | 0 | 6 | 2 |
| B | 1 | 3 | 3 |
| C | 2 | 1 | 1 |
| D | 4 | 2 | 4 |

先找事件时刻。三个非抢占算法在时刻 0 都只能启动 A。时刻 6，B、C、D 全部在就绪队列，FCFS 选 B，SJF 选 C，优先级调度选 D。RR 在时刻 2 已收到 B，此刻又收到 C，因此队列变成 `[B, C, A]`。时刻 4 正好到达 D，此时 C、A 已在队里，队列变成 `[C, A, D, B]`。

```text
FCFS：        0─A─6─B─9─C─10─D─12
非抢占 SJF：  0─A─6─C─7─D─9─B─12
非抢占优先级：0─A─6─D─8─B─11─C─12
RR（q=2）：   0─A─2─B─4─C─5─A─7─D─9─B─10─A─12
SRTF：        0─A─1─B─2─C─3─B─5─D─7─A─12
```

从图上读三个时刻。设任务到达为 `a`，首次运行是 `s`，结束是 `c`。

- **响应时间** = `s - a`，只等第一次拿到 CPU。
- **周转时间** = `c - a`，从到达到全部完成。
- **等待时间**是所有在就绪队列里等 CPU 的区间之和。本题只有 CPU 执行时间 `b`，所以可用 `c - a - b`。有 I/O 的题要单独区分阻塞时间。

| 算法 | 完成时刻（A/B/C/D） | 等待时间（A/B/C/D） | 平均等待 |
| --- | --- | --- | ---: |
| FCFS | 6 / 9 / 10 / 12 | 0 / 5 / 7 / 6 | 4.50 |
| 非抢占 SJF | 6 / 12 / 7 / 9 | 0 / 8 / 4 / 3 | 3.75 |
| 非抢占优先级 | 6 / 11 / 12 / 8 | 0 / 7 / 9 / 2 | 4.50 |
| RR | 12 / 10 / 5 / 9 | 6 / 6 / 2 / 3 | 4.25 |
| SRTF | 12 / 5 / 3 / 7 | 6 / 1 / 0 / 1 | 2.00 |

RR 下 A 时刻 0 就开始，响应时间为 0。它在 `[2,5)` 和 `[7,10)` 等了共 6 个单位。**检查甘特图**时，先加总每个任务的执行片段，确认和题面给出的执行时间相同，再核对有没有画出早于到达时刻的片段。

### 为什么要用多级队列？

任务类型固定时，多级队列（MLQ）可以让交互任务进入一条队列、批处理任务进入另一条，各用不同规则。多级反馈队列（MLFQ）则根据运行表现调队。课件例子中，新任务进入 Q0，用 8 ms 的时间片。用完配额还没结束，降到 Q1 再跑 16 ms。仍有剩余就进 Q2，按 FCFS。一个纯 CPU 任务需要 30 ms，且没有别的任务时，三个队列分别运行 `8 → 16 → 6` ms。短任务往往在高层结束，老化或周期性提升可缓解低层长期等不到 CPU。

其他课件考点先掌握含义。SJF 不知道下一段要多久时，可用历史值做指数预测 `新预测 = α × 本次实测 + (1−α) × 旧预测`。多核的每核队列需要负载均衡，CPU 亲和性则尽量保留缓存收益。实时题先分清 RM 按周期给固定优先级，EDF 每次比较当前请求的绝对截止时间。排队题的 Little 定律是 `平均排队人数 = 平均到达率 × 平均排队时间`，人数与时间都只取队列部分。

## 6. 两个线程各加一次，为什么结果只加了一次？

假设 `count=5`。`count++` 会读旧值、加 1、写回。A 读到 5 后被换下，B 也读到 5。两边各自把 6 写回，最终还是 6。这是**竞争条件**，执行交错影响结果，丢失了一次更新。单核交错也能发生。

访问共享状态的这段代码叫**临界区**。给两个线程共同使用一把锁，先获得锁的线程完成整个“读 → 算 → 写”，另一边拿到锁时才读到更新后的值。**互斥**解决谁能同时进去。**同步**还要表达谁在等什么，比如消费者等缓冲区出现数据。

| 正确性要求 | 用一道判断来记 |
| --- | --- |
| 互斥 | 两个人可以同时进入同一个临界区吗？不可以。 |
| 前进 | 临界区空着，而且有人想进。可以让一个毫无进入意愿的进程一直挡着吗？不可以。 |
| 有限等待 | 一个进程已经提出进入请求，别人可以无限次插队吗？不可以。 |

**严格轮换**只有 `turn`。线程 A 用完后将 `turn` 交给 B，即使 B 没兴趣，A 也要等，因而违反前进。**Peterson** 多加一组 `flag` 表示是否想进。线程 `i` 先设 `flag[i]=true`，再设 `turn=j`。只有 `flag[j] && turn==j` 同时成立才等，离开时清自己的 `flag`。双方同时申请时，最后写 `turn` 的一方把优先权让给另一方。这个推导采用课件的顺序一致性假设。

### 软件的检查和修改怎样做成一步？

- **关中断**可以限制本核的一些交错，其他核仍能访问同一份数据。解释多处理器题时，直接写出另一个核不受本核关中断影响。
- **TAS（Test-and-Set）**原子地读取锁的旧值并置位。旧值为假就表示自己拿到空闲锁。**CAS（Compare-and-Swap）**原子地比较并按条件写入。用 CAS 加一时，读旧值 → 尝试把它替换为旧值加 1 → 比较失败则重新读并重试。
- **自旋**在 CPU 上反复检查，持锁时间短且持锁者可在另一核继续运行时有价值。**阻塞**把等待者挂到队列并让出 CPU，持锁时间长时可减少空转，但有阻塞、唤醒和调度开销。
- **访问顺序**是另一个问题。发布者先写 `data`，再对 `ready` 做 release 写。读取者用 acquire 读到这次发布后，才读取 `data`。这样可以把对数据的写入和后续读取建立同步关系。

## 7. 只有一把锁，为什么消费者还是没法工作？

把缓冲区想成有几个位置的传菜台。互斥锁只能保证两个人不会同时动台面。服务员即使拿到了锁，也可能看到空台面，需要等待厨师放菜。厨师看到台面满，也要等服务员腾出位置。于是需要两个独立的许可，再用一把锁保护实际放取。

| 同步对象 | 初值 | 申请了什么 | 什么时候归还或发出许可 |
| --- | ---: | --- | --- |
| `mutex` | 1 | 独占修改缓冲区与读写位置 | 修改完成后释放 |
| `empty` | N | 一个可以使用的空位 | 消费者取走一个项目后发布 |
| `full` | 0 | 一个可以取出的项目 | 生产者放入一个项目后发布 |

```text
生产者循环                       消费者循环
    item = produce()                P(full)
    P(empty)                        P(mutex)
    P(mutex)                        item = get()
    put(item)                       V(mutex)
    V(mutex)                        V(empty)
    V(full)                         consume(item)
```

**沿着容量为 2 的台面走一遍。** 起初空位有 2，数据有 0。生产者连续放完 A、B 后，可用空位为 0，消费者可取 2 项。生产者想放 C，先在 `P(empty)` 等待，此时还能让消费者拿到 `mutex`。消费者取走 A 并执行 `V(empty)`，等待中的生产者得到空位许可，之后才争取 `mutex` 并放 C。若把生产者的两次 P 写成先拿锁再等空位，满时消费者就拿不到腾空位所需的锁。

### P/V 内部在数什么？

`P` 原子地申请许可，当前没有可用许可时等待。`V` 归还或发布许可，有等待者时可以唤醒一个。课件的**阻塞式实现**用负数编码等待人数，例如初值 1，A 执行 P 后计数 0。B、C 再分别执行 P 后，变成 −1、−2，两人都阻塞。A 执行 V，计数变成 −1，唤醒一位，仍有一位等待。负值描述这一信号量的等待队列。不同接口对外暴露的取值规则可以不同。

同一个信号量还能表达先后。要保证 `S1` 先于 `S2`，设 `done=0`。线程 A 做完 `S1` 执行 `V(done)`，线程 B 先 `P(done)` 再做 `S2`。A 先跑时许可会留下，B 先跑时会先等。互斥量一般由持锁者解锁，信号量允许一个执行者发布许可、另一个执行者取得许可。

## 8. 等的条件从“有几个”变成“当前状态满足什么”，怎么办？

还是一格传菜位，但这次用一个共享布尔值 `full` 表示有无菜。要安全地等待，服务员得先持锁检查 `full`。若空着，就得把锁交出去，让厨师进来改变状态。**条件变量把释放锁与进入等待连成一个原子步骤**。被唤醒后，等待者重新取得锁，再从等待调用返回。

```text
厨师                                  服务员
    lock(m)                               lock(m)
    while full:                           while !full:
        wait(not_full, m)                     wait(not_empty, m)
    放菜                                  取菜
    full = true                           full = false
    signal(not_empty)                     signal(not_full)
    unlock(m)                             unlock(m)
```

服务员先来时，拿锁看到 `full=false`，再等待 `not_empty` 并释放锁。厨师拿锁，放菜，把 `full` 改成 `true`，通知服务员，然后解锁。服务员重新拿到锁后再检查一次。为什么用 `while`？因为从收到通知到重新拿锁之间，别的服务员可能已把菜取走，条件也可能因其他原因仍不满足。

- **管程**把共享数据、相关操作和同步规则封装在一起，一次只允许一个执行者在管程内执行。入口队列中的人在等进入权，条件队列中的人在等共享状态变化。
- **信号量的 V** 在无人等待时可以留下一个许可。**条件变量的 `signal`** 无人等待时不留下通知，真正能让后来者继续的是共享状态已经满足条件。
- 课件讨论两种通知语义。Hoare 风格在通知时把管程立即交给被唤醒者。Mesa 风格让通知者先继续，被唤醒者之后再竞争锁。POSIX 的 `pthread_cond_wait` 和 Java 对象的 `wait` 都要按实际共享条件写循环检查。Java 的 `notify()`、`notifyAll()` 发完通知后，通知者仍持有对象锁，直至退出相应同步区域。

## 9. 换一种共享约束，锁放在哪？

### 读者—写者：读可以并行，写要独占

多个读者可以同时查看房间设置。房主改地图和模式时，需要独占这两项数据，否则其他人可能读到一半新一半旧的设置。把活跃读者组织成一组，**第一个读者获取数据访问权，最后一个读者释放**。组内读者各自读取，写者单独获取访问权。

```text
初值：read_count = 0，mutex = 1，rw_mutex = 1

读者进入                              读者退出
    P(mutex)                              P(mutex)
    read_count += 1                       read_count -= 1
    if read_count == 1:                   if read_count == 0:
        P(rw_mutex)                           V(rw_mutex)
    V(mutex)                              V(mutex)
    read()

写者：P(rw_mutex) → write() → V(rw_mutex)
```

`mutex` 保护读者计数，`rw_mutex` 保护实际的数据访问权。假设 R1、R2 先后进入，R1 把计数从 0 变成 1 并取访问权，R2 把计数变成 2。R1 退出时计数降到 1，仍有读者在工作。R2 把计数降到 0，写者才有机会进入。这是读者优先方案，读者接连到来时，写者可能长期等待。

### 哲学家就餐：一次申请需要两侧资源

把请求者状态画成 `THINKING → HUNGRY → EATING → THINKING`。管程方案中，`pickup(i)` 把第 i 人置为 `HUNGRY`，再调用 `test(i)`。如果左右邻居都没在吃，就把 i 置为 `EATING`，并允许其继续。否则 i 等自己的条件变量。`putdown(i)` 归还资源，把自己置回 `THINKING`，再分别检查左右邻居的申请是否能满足。关键是检查双方资源和登记占用都在同一个管程中完成。

从接口名称识别工具。`pthread_mutex_lock/unlock` 保护临界区，`sem_wait/post` 操作许可，`pthread_cond_wait/signal` 用于共享条件。Java 的 `synchronized` 保护对象临界区，`wait/notifyAll` 配合对象锁。有名 POSIX 信号量用名字让多个进程找到同一个对象，无名信号量按初始化方式在同一进程使用或放到共享内存供多进程使用。
